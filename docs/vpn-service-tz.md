# ТЗ: подписочный VPN-сервис (MVP с фундаментом для масштабирования)

## 1. Цель

Создать потребительский VPN-сервис для пользователей из России с простой схемой:

1. Пользователь открывает Telegram-бота.
2. Выбирает подписку за 200 ₽ в месяц.
3. Переходит в личный кабинет без отдельной регистрации.
4. Оплачивает картой или через СБП на странице платёжного провайдера.
5. Добавляет устройство и копирует его персональный subscription URL в Happ.
6. Пользуется доступом до окончания подписки.

Пользователь не управляет серверами и не получает новый ключ при замене VPN-ноды. Платформа самостоятельно поддерживает актуальный список доступных нод.

## 2. Границы первой версии

### В MVP входит

- Telegram-бот и вход по Telegram user_id;
- личный кабинет в вебе;
- один тариф: 200 ₽ / 30 календарных дней;
- оплата через эквайринг: карта и СБП;
- автоматическое подтверждение оплаты webhook-ом;
- до трёх активных устройств на тарифе; у каждого — отдельный персональный subscription URL;
- VLESS/Xray-ноды минимум в 2 странах;
- выдача актуального списка нод в Happ;
- админ-панель для пользователей, платежей, подписок и нод;
- мониторинг нод и исключение недоступной ноды из выдачи.

### Не входит в MVP

- собственные приложения для iOS/Android/Windows;
- автопродление и хранение платёжного метода;
- реферальная программа, промокоды и партнёрская система;
- сложный балансировщик трафика;
- десятки тарифов и индивидуальные пакеты.

## 3. Пользовательские сценарии

### Покупка

Бот показывает тариф и кнопку «Оформить подписку». По кнопке открывается кабинет с проверенной Telegram-сессией. Пользователь выбирает «1 месяц — 200 ₽», нажимает «Оплатить» и попадает на платёжную страницу эквайринга.

После подтверждения платежа провайдер отправляет webhook. Только после серверной проверки платежа подписка становится активной. Бот и кабинет показывают дату окончания.

### Подключение VPN

В кабинете пользователь видит устройства, их статус и кнопку «Добавить устройство» (до трёх на стартовом тарифе). У каждого устройства — отдельная кнопка «Скопировать ключ», инструкция по добавлению ссылки в Happ и действие «Отозвать доступ». Вставляет URL в Happ и видит доступные страны.

### Продление

Если подписка активна, новый месяц прибавляется к текущей дате окончания. Если истекла — срок начинается с момента успешной оплаты.

### Замена ноды

При недоступности нода исключается из выдачи subscription API. Пользователь обновляет подписку в Happ или ждёт её автоматического обновления; новый ключ не нужен.

### Окончание подписки и отзыв устройства

Каждая VPN-нода получает срок действия доступа устройства и сама принудительно блокирует его после окончания этого срока. Удаление устройства в кабинете или админке инициирует срочную блокировку на всех нодах. Если одна нода временно не подтвердила команду, задача повторяется и отображается в админке как незавершённая.

## 4. Архитектура

### Принцип

Разделить control plane и VPN data plane.

- **Control plane:** кабинет, бот, пользователи, платежи, подписки, управление нодами, генерация конфигураций.
- **Data plane:** изолированные VPS с Xray, которые обслуживают только VPN-трафик.

Backend запускается как модульный монолит: один репозиторий и развёртывание, но независимые доменные модули `auth`, `billing`, `subscriptions`, `nodes`, `orchestrator`, `admin`, `notifications`.

### Компоненты

| Компонент | Назначение |
|---|---|
| Telegram Bot | Онбординг, кнопка кабинета, уведомления о платеже и окончании срока |
| Web / Personal cabinet | Тариф, платёж, ключ, инструкция, статус подписки |
| API | Бизнес-логика, авторизация, выдача subscription URL |
| PostgreSQL | Источник правды о пользователях, заказах, платежах, подписках и нодах |
| Redis + worker | Очереди: обработка webhook, уведомления, синхронизация нод, проверки |
| Subscription API | Быстро выдаёт персональный набор конфигураций Happ |
| Node orchestrator | Добавляет/отзывает пользователей на Xray-нодах, применяет конфигурации |
| Xray/VLESS nodes | Обслуживают трафик пользователей |
| Admin panel | Поддержка, аудит, ручные безопасные операции |

### Масштабирование

- API и workers не хранят состояние в памяти: их можно горизонтально масштабировать.
- Subscription API отделяется первым при росте нагрузки и кэширует краткоживущие ответы в Redis.
- Ноды добавляются как записи в реестр нод; новая нода не требует изменения клиентских ключей.
- Пользовательский трафик не проходит через API, базу или Telegram-бота.
- Для каждой страны поддерживается резервная нода и лимиты на пользователей/пропускную способность.

### Устойчивость пула соединений

- Пользователь получает доступ к логическому пулу, а не к конкретному IP, VPS, провайдеру или transport profile.
- Физическая нода, endpoint и connection profile имеют независимые lifecycle и availability-состояния.
- Одна физическая нода может предоставлять несколько версионируемых профилей подключения; замена или отключение одного профиля не требует менять подписку, пользователя или платёж.
- Subscription API формирует список из пригодных endpoint/profile и автоматически исключает деградировавшие варианты после подтверждения несколькими независимыми сигналами.
- Доступность проверяется не только из дата-центра: перед коммерческим запуском обязательны внешние probes из целевых сетей, отдельные проверки DNS, IPv4/IPv6, transport/VPN handshake и выхода в интернет через туннель.
- Частичная недоступность у одного оператора не приравнивается к полному падению VPS. Система хранит региональное состояние и по возможности не выдаёт проблемный маршрут затронутой сети.
- Ни один provider, ASN, регион, IP family или профиль подключения не является обязательной единственной зависимостью production-пула.
- Автоматизация сначала переводит проблемный ресурс в quarantine и прекращает новую выдачу. Удаление VPS требует отдельного подтверждённого действия.
- Новые версии профилей и data-plane software вводятся поэтапно с canary, периодом наблюдения и rollback.
- При массовой деградации control plane включает аудируемый Emergency Mode: останавливает плохую выдачу, активирует независимый резерв, перестраивает subscription feed и уведомляет администратора.

## 5. Модель данных (минимум)

| Сущность | Ключевые поля |
|---|---|
| users | id, telegram_id (unique), username, created_at, status |
| sessions | id, user_id, expires_at, revoked_at |
| plans | id, name, price_rub, duration_days, device_limit, active |
| orders | id, user_id, plan_id, amount, currency, status, idempotency_key, expires_at |
| payments | id, order_id, provider, provider_payment_id (unique), status, amount, paid_at, raw_event_reference |
| subscriptions | id, user_id, starts_at, ends_at, status |
| devices | id, user_id, name, status, created_at, revoked_at, last_seen_at |
| subscription_tokens | id, device_id, token_hash, revoked_at, last_used_at |
| nodes | id, country, endpoint, status, capacity, current_load, last_healthcheck_at |
| endpoints | id, node_id, host, port, ip_family, provider, asn, region, lifecycle_status, availability_status |
| connection_profiles | id, endpoint_id, protocol_type, transport_type, security_type, version, priority, rollout_status, availability_status |
| probe_results | id, probe_id, endpoint_id, profile_id, network_label, check_type, status, latency, observed_at |
| node_assignments | id, user_id, node_id, status, applied_at |
| node_sync_jobs | id, node_id, desired_config_version, status, attempts, acknowledged_at |
| audit_log | actor, action, entity_type, entity_id, metadata, created_at |

Токен из URL — длинный криптографически случайный секрет. В базе хранится только его хеш. Telegram ID и последовательные ID в ссылку не попадают.

## 6. Платёжный контур: обязательные правила

1. Создать `order` до перехода пользователя к оплате.
2. Для одного заказа создавать один платёж; повторное нажатие «Оплатить» возвращает к существующему незавершённому платежу.
3. Использовать ключ идемпотентности при создании платежа.
4. Страница возврата от эквайринга ничего не активирует: она только сообщает «Проверяем оплату».
5. Подписку продлевает только backend после webhook-а и запроса к API эквайринга за актуальным статусом.
6. Сверять: provider_payment_id, order_id, пользователя, сумму, валюту и итоговый статус `succeeded`.
7. Повторный webhook или повторная задача в очереди не могут продлить подписку дважды.
8. Все переходы состояния платежа и подписки выполняются одной транзакцией БД.
9. При задержке webhook-а показывать «Платёж обрабатывается», а worker периодически проверяет статус у провайдера.
10. Секреты эквайринга живут только в secret storage на backend и никогда не передаются в браузер, бота или Git.
11. В админке должны быть поиск по Telegram ID, номеру заказа и ID платежа, а также история событий.
12. Возврат — отдельная ручная операция с ролью администратора и обязательной записью в audit log.

## 7. Безопасность и защита от ошибок

- Проверять подпись/подлинность webhook и сверять статус через API провайдера.
- Ограничить частоту создания заказов, входов, API-запросов и запросов subscription URL.
- Использовать HTTPS везде; отдельно защитить домен кабинета и домен подписок.
- Дать пользователю возможность отозвать subscription URL и выпустить новый при утечке.
- Ограничить число устройств параметром тарифа; стартовый тариф даёт до трёх именованных устройств. Лимит редактируется из админки, а не меняется в коде.
- У каждого устройства своя ссылка. Нельзя делить один и тот же URL между всеми устройствами.
- Ограничить одновременные подключения для одного устройства и фиксировать аномальное число разных IP без хранения содержимого трафика.
- У каждой ноды должен быть локальный срок действия доступа устройства: истечение подписки не зависит только от очередного обновления Happ.
- Ссылку устройства можно немедленно отозвать или перевыпустить из кабинета и админки.
- Не хранить пароли и данные карт.
- Сделать ежедневные резервные копии PostgreSQL и регулярно проверять восстановление.
- Собрать мониторинг: доступность API, webhook-ошибки, очередь, здоровье нод, заполнение диска, трафик и долю ошибок подключения.
- Админка: отдельные роли, 2FA, журнал всех ручных действий.

## 8. Нефункциональные требования

- После подтверждённой оплаты доступ активируется обычно менее чем за 1 минуту.
- Subscription API должен работать при недоступности отдельной VPN-ноды.
- Персональные URL не индексируются и не отображаются в логах целиком.
- Любая нода может быть выведена из эксплуатации без смены ключа у пользователя.
- База данных — единственный источник срока подписки; кеш не принимает финансовых решений.
- Система допускает запуск нескольких экземпляров API и workers.
- Отзыв устройства доставляется на все healthy-ноды с подтверждением; целевой срок — не более 5 минут.
- Истечение подписки блокируется на ноде локально, даже если control plane временно недоступен.
- Subscription URL не меняется при замене IP, VPS, endpoint или connection profile.
- Production-пул выдерживает потерю одного provider/ASN или региона за счёт заранее подготовленного независимого резерва.
- Решение об автоматическом исключении использует настраиваемые пороги, кворум probes, cooldown и разные failure/recovery thresholds; кратковременная ошибка не уничтожает исправный VPS.
- Администратор видит причину деградации без SSH: последние heartbeat/probes, затронутые сети и IP family, profile version, rollout, capacity, историю переходов и активные алерты.

## 9. План реализации

### Этап 0. До разработки

1. Подтвердить, что выбранный эквайринг готов подключить данную категорию сервиса.
2. Оформить юридическую сторону приёма платежей, пользовательское соглашение, политику конфиденциальности, порядок возврата и выдачу чеков.
3. Купить домен, определить название и поддержку.
4. Подготовить тестовый аккаунт эквайринга.

### Этап 1. Технический прототип

1. Поднять одну Xray/VLESS-ноду.
2. Подключить Happ вручную и проверить конфигурации.
3. Сделать PostgreSQL-схему, backend и один subscription URL.
4. Добавить вторую ноду и проверить, что её можно убрать без смены ключа.

### Этап 2. Продуктовый MVP

1. Реализовать Telegram-бота и безопасный вход в кабинет.
2. Сделать кабинет: статус, ключ, инструкция, кнопка оплаты.
3. Подключить тестовую оплату, webhook и обработку всех статусов.
4. Реализовать админку и журнал операций.
5. Провести тесты: двойной клик, два webhook-а, закрытая страница, отмена, задержка и возврат.

### Этап 3. Подготовка к реальным пользователям

1. Подключить боевой эквайринг и чеки.
2. Добавить мониторинг, алерты, бэкапы и восстановление.
3. Ввести health checks и автоматическое исключение ноды.
4. Добавить модель endpoint/profile, внешние probes, quarantine и anti-flapping до автоматического удаления или замены инфраструктуры.
5. Открыть закрытую бету на небольшой группе, вручную сопровождать первые платежи и обращения.

### Этап 4. Контроль рисков до публичного запуска

1. Утвердить правила разумного использования и не обещать безусловный безлимитный трафик до подтверждения экономики.
2. Провести нагрузочный тест на одновременные подключения, трафик и синхронизацию нод.
3. Описать обработку abuse-жалоб и процедуру срочной замены ноды.
4. Утвердить политику приватности, минимальный состав логов и сроки хранения данных с юристом.
5. Провести аварийную тренировку: недоступность ноды, platform VPS, Telegram, DNS и задержка webhook.
6. Подготовить статус-страницу, резервный канал поддержки и инструкции для пользователей при сбое.
7. Проверить staged rollout/rollback и Emergency Mode на тестовом пуле без реальных пользовательских credentials.

## 10. Что делать прямо сейчас

1. Не писать весь сервис сразу.
2. Сначала подтвердить эквайринг и правовую возможность принимать платежи за сервис — это главный бизнес-риск.
3. Параллельно выбрать название и домен.
4. Затем построить технический прототип «Happ → subscription URL → две заменяемые ноды» без оплаты.
5. Только после успешного прототипа приступать к кабинету, боту и платежам.

## 11. Критерий готовности MVP

Новый пользователь из Telegram может оплатить 200 ₽ картой или СБП, в течение минуты получить активную подписку, добавить до трёх устройств и подключить Happ. При отключении одной ноды она исчезает из следующего обновления подписки, а срок доступа и ключи остальных устройств не меняются. После истечения подписки или отзыва устройства каждая healthy-нода блокирует соответствующий доступ не позднее чем за 5 минут.
